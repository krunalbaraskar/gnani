## Problem Statement

A sales rep is on a call. The client asks how much stock there is of one item and what
the bulk rate is. The rep knows the answer is in a spreadsheet somewhere, stalls, and
says "I'll get back to you". In a project meeting the same thing happens with "what did
we agree on delivery last time?". Asking an AI in front of the client is embarrassing,
and a generic AI does not know the rep's inventory or project anyway.

Echo today transcribes both sides of a call with Gnani speech-to-text and suggests a
generic reply. It does not know anything about the user's business, it has never been
run on Windows, and it looks like a utility window.

## What Makes This Cool

The client asks, and a couple of seconds after their sentence ends the exact figure
from your own files is on your screen with the file it came from, in a glass bar nobody
on the screen share can see. You never left the call, and nobody knows you looked
anything up.

The conversation is in mixed language, the way Indian business calls are: Hindi with
English product names, a regional word here and there. Gnani's speech-to-text gets the
words down, and Echo adds a plain meaning under any line that mixes in words you may not
know. And when the thing you need is on your screen, not in a file, you can ask Echo to
read the screen.

Among the products found in a web search on 2026-10-09: Indian voice AI products
(Edesy, SquadStack, DotCall, Voicegenie) are outbound bots that replace the rep, and the
open-source Cluely clones (Pluely, OpenCluely) are English-first and read the screen.
None of those combines Indian code-mixed speech with answers from the user's own files.

## Constraints

- Judged from the GitHub repo plus a recorded demo video. The scripted replay demo is
  the critical path; live mic and system audio must work on Windows but are not on it.
- No new vendors and no new runtime dependencies. Answers, meanings and screen reading
  go through the OpenAI-compatible LLM already configured. Gnani stays the only speech
  provider.
- API keys stay in the main process. Context files and screen captures are handled only
  in the main process.
- The Gnani protocol has never been run against the real API (9 `TODO(verify-gnani)`
  items in `src/core/stt/gnani-protocol.ts`).
- Ruled out by the user: making the user "speak any language". Language is also
  pronunciation and fluency, and reading a line off a card does not supply those.

## Premises

1. The headline is answers from the user's own context, shown live during the call.
2. Being hidden from screen share is a headline feature, not a footnote: it is what
   makes it safe to use in front of a client.
3. The language layer helps the user understand mixed-in native words. It does not put
   words in another language in the user's mouth.
4. Judging is repo plus video, so the scripted replay demo must be repeatable.
5. The overlay takes Cluely's current shape: a slim glass bar at top-centre that expands
   into a panel.
6. No new vendors or runtime dependencies.
7. Echo can read the screen, but only when the user asks. It never watches the screen
   on its own.

## Approaches Considered

Retrieval, the one open design choice:

### Approach A: Send everything, fall back to keyword retrieval (chosen)

If the context folder is small, the whole of it goes into the prompt. If it is larger,
the files are split into chunks and the best-matching chunks are picked by word overlap
with the question. No extra services. Works with a local model as long as its context
window fits the context budget.

### Approach B: Embeddings and a vector index

Better matching when the question and the file use different words. Not chosen: it
needs an embeddings endpoint, which many OpenAI-compatible servers do not offer, plus an
index to build and store. It is the upgrade path if keyword matching misses too often.

### Approach C: Let the model call a "search files" tool

Not chosen: tool calling is uneven across the small and local models this app supports,
and each lookup adds a round trip during a live call.

Dropped during the session: "speak any language" (ruled out by the user, see
Constraints), and keeping the current side window with a restyle.

### Everything answers during a call

Automatic answers, the answer hotkey, typed questions and screen reading all work only
while a call (live or replay) is running. Outside a call the Ask box is disabled with
"Start a call to ask", and the hotkeys show the existing notice "Start a session first".
One rule, and it matches how the code is built: the answer engine lives inside the
session.

### Context folder

- The user picks one folder in the Context tab through the native folder dialog in the
  main process, the same pattern the export folder uses. The renderer can never set the
  path. The setting is `contextDir` (empty by default).
- Files read: `.txt`, `.md`, `.csv`, `.tsv`, `.json`, top level of the folder only;
  subfolders are ignored and not listed. Other file types are listed as skipped with the
  reason (for example "PDF not supported"). Limits, applied in file-name order: 1 MB per
  file ("too large"), 4 MB in total ("folder over 4 MB"), 50 files ("over the 50-file
  limit").
- Encoding: a UTF-8 byte-order mark is stripped. A file starting with a UTF-16
  byte-order mark is decoded as UTF-16. Anything else is decoded as strict UTF-8, and a
  file that is not valid UTF-8 is skipped with "not UTF-8: save as CSV UTF-8". Garbled
  text is never sent to the model.
- Loaded at call start and when the user presses Reload. Not watched for changes.
  Reload during a call applies from the next answer.
- Folder set but unusable: "Context folder could not be read" with the system's reason,
  or "No readable files in this folder", shown in the Context tab and on the bar. In
  both cases answers behave as if no folder were set.
- The Context tab lists every file with its size or row count and states that the
  contents are sent to the configured AI model.

### Context engine (new, `src/core/context/`, no Electron imports)

- Chunking: `.csv` and `.tsv` are split into rows at line breaks that are outside
  double quotes, then into groups of up to 20 rows, each prefixed with the header row. A
  group is cut short so no chunk exceeds 2,000 characters; a single row longer than that
  is cut at 2,000. Other files, `.json` included, are treated as text: split on blank
  lines, and any block over 800 characters is split again at line breaks, then at 800
  characters if one line is longer. Every chunk carries its file name.
- Budget: setting `contextBudgetChars`, default 24,000, adjustable in Settings from
  4,000 to 100,000 with the hint "lower this for small local models". If the model
  rejects the prompt as too long, the Answer card shows the model's error and "Lower the
  context budget in Settings".
- Selection: if all chunks together fit the budget, all of them are sent. Otherwise:
  query words that occur in more than half of all chunks are ignored; each chunk is
  scored by how many of the remaining distinct query words it contains, rarer words
  counting more; chunks scoring above zero are taken best first, ties by file name then
  position; a chunk that does not fit the remaining budget is skipped and the next is
  tried. If no chunk scores above zero, no file chunks are sent, so the answer cannot be
  shown as "from your files". Words are lower-cased and split on anything that is not a
  letter or digit, Unicode-aware.
- Query: the question being answered plus the last three "them" lines.
- Known limit: above the budget, a question whose words do not appear in the file can
  miss, including English product names that speech-to-text returns in Devanagari. Small
  folders are sent whole, so the demo path is not affected. Marked in code with a
  `ponytail:` comment naming embeddings as the upgrade.

### Answers (extends `src/core/suggest/`)

- The suggestion card becomes the Answer card. Triggers: automatically when "them" asks
  a question (the existing detector and 8-second cooldown), the answer hotkey
  Ctrl+Shift+Space, a question typed into the Ask box, and the screen hotkey.
- The prompt gets a block "My files" holding the selected chunks under their file
  names. File contents, and anything read from a screenshot, are reference data and
  never instructions.
- System prompt rules: take facts (stock, price, dates, terms) only from My files, the
  note about me, the transcript, or the screen when one is attached; if the needed fact
  is in none of them, say so and give one polite line the user can say to buy time; end
  with one line `[source: ...]` listing what was used: file names, `transcript`, `note`,
  `screen`, `none` when the reply needs no fact, or `missing` when the fact could not be
  found.
- Parsing: the last line matching `[source: ...]` is removed from the text and becomes
  the source list. A file name counts only if it matches, ignoring case, surrounding
  spaces and any folder prefix, a file whose chunks were sent in that request; other
  names are dropped. No such line is treated as `none`. While streaming, a trailing line
  starting with `[` is hidden until it completes.
- Number check, in code, after the answer finishes: every number in the answer must
  appear in the chunks that were sent, the note, the transcript or the typed question.
  Numbers are compared as whole tokens, never as substrings, after removing commas and
  currency signs, dropping trailing zeros after a decimal point, and turning
  Indian-script digits into 0-9. A figure the model worked out itself, or one the
  sources hold only as words, fails the check. That is an accepted limit: a false "check
  this figure" is cheap, a false "from your files" is not.
- While an answer is streaming the card is titled "Answer · checking", in the neutral
  style with no source chips. It takes its final title and style only when the verdict
  is known. The user can read the words as they arrive, but nothing claims they are
  verified until they are.
- `Suggestion` gains `sources`, `asked` (the typed question), `usedScreen` and
  `verdict`. The verdict is one ordered rule; the first match wins:
  1. The source line contains `missing`: `missing`. Title "Answer · not in your files",
     dashed border.
  2. A screenshot was attached: `screen`. Title "Answer · from your screen", file chips
     too if files were cited. The number check does not run. The card carries the small
     note "read by the AI model, not checked".
  3. No context folder is loaded: `reply`. Title "Suggested reply", as today. The
     number check does not run.
  4. The source is `none` or absent: `reply`. Title "Suggested reply". The number check
     does not run, because a plain reply claims no source.
  5. The number check fails: `unverified`. Title "Answer · check this figure", amber
     border, no source chips.
  6. At least one valid file source: `files`. Title "Answer · from your files", file
     chips shown.
  7. `transcript` or `note` cited: `call`. Title "Answer · from this call" if the
     transcript was cited, otherwise "Answer · from your note".
  8. File names were cited but all were dropped: `unverified`.
     A typed question shows "you asked" after the title.
- Precedence between triggers: a typed question, the answer hotkey and the screen hotkey
  cancel whatever is in progress, are never held back by the cooldown, and do not reset
  it. An automatic answer never interrupts one that is streaming, and does not replace a
  typed, hotkey or screen answer until 8 seconds after it finished.
- Held-back automatic answers: a caller question that arrives while an automatic answer
  cannot run is kept, the newest one only. It runs as soon as nothing is streaming, the
  cooldown has ended and the 8-second protection above has passed, provided that moment
  is within 20 seconds of the question arriving; otherwise it is dropped. So the demo's
  stock, bulk-rate and delivery questions each get an answer in turn.
- Reply language keeps the existing three choices. Nothing asks the user to speak a
  language they do not know.

### Reading the screen when asked (new, `src/main/screen-capture.ts`)

Added at the user's request during review of this doc.

- When: only on an explicit ask, during a call. Two ways: the global hotkey
  Ctrl+Alt+Space, and a screen toggle on the Ask box that attaches the screen to the
  typed question and switches itself off after each question. Nothing captures the
  screen in the background, and automatic answers never include it. If the hotkey
  cannot be registered because another program holds it, the existing "hotkey taken"
  notice is shown and the toggle still works.
- Enabled only when the setting `llmVisionModel` is filled in. Many servers silently
  ignore an image sent to a text-only model and answer anyway, so Echo does not guess:
  the user names a model that can read images. Until then the toggle and hotkey show
  "Set a vision model in Settings to use the screen". Screen requests go to that model.
- Capture, one code path on every platform: make the overlay invisible, wait 100 ms,
  capture one still of the display the mouse pointer is on with Electron's
  `desktopCapturer` in the main process, then make the overlay visible again in a
  `finally` block so it always comes back. The image is scaled so its longer side is at
  most 1,568 px and encoded as JPEG.
- Where it goes: into that one request, as an image part next to the text (the
  OpenAI-compatible `image_url` form with a data URL), along with the transcript and
  selected file chunks. It is held in memory only, never written to disk, never sent to
  the renderer, and not put in the export. The export records only that the screen was
  used for that answer.
- The hotkey with no typed question asks: "Answer the question or explain what is on my
  screen, using my files where they help."
- Failures: if the capture fails or returns an empty image (for example macOS without
  screen-recording permission), the card shows "Could not read the screen" with the
  reason and no request is sent. If the server rejects the image, the card shows "This
  model cannot read images. Set a vision model in Settings." Nothing is retried.
- Known limit, stated in the README: a screen answer is what the model read off the
  picture. Echo cannot check it, and says so on the card.
- Types: `ChatMessage.content` in `src/core/llm/types.ts` becomes text or a list of
  text and image parts. The mock LLM server accepts image parts so the path is tested
  offline.

### Meaning line (new, `src/core/gloss/`)

- Setting `myLanguage`: one of the ten plain entries of `GNANI_LANGUAGES` (hi-IN, en-IN,
  ta-IN, te-IN, kn-IN, ml-IN, mr-IN, bn-IN, gu-IN, pa-IN), default en-IN. Setting
  `explainThem`: boolean, default true.
- For each final "them" line the engine asks the model: if the line contains words that
  are not in `myLanguage`, give the plain meaning of the whole line in `myLanguage`, in
  that language's usual script, in at most 20 words; otherwise answer with a single `-`.
  The caller's line is data, never an instruction. A `-` or an empty answer shows
  nothing.
- One request at a time, in order. A line that has waited more than 6 seconds is
  skipped. A request that errors or takes more than 8 seconds is dropped. In both cases
  the line simply has no meaning under it; the transcript is never blocked or reordered.
  Clicking any "them" line requests its meaning again; that request goes to the front of
  the queue and is exempt from the 6-second rule.
- A meaning request never delays an answer: when an answer starts, a meaning request in
  flight is cancelled and its line goes back to the front of the queue.
- When a call stops, queued and in-flight meaning requests are cancelled. The export
  holds the meanings that had arrived.
- `TranscriptSegment` gains optional `meaning`.

### Overlay (renderer rebuild, `src/renderer/`)

- Window: frameless, transparent, always on top, 620 px wide, centred horizontally, 12
  px below the top of the work area. Width is fixed. Height follows the content: the
  renderer watches its root element with a `ResizeObserver` and sends the existing
  `resize` window command; the main-process clamp changes to height 44 to 640. The
  bottom-right resize grip is removed. `ECHO_OPAQUE_WINDOW=1` keeps working as the
  fallback for GPUs that draw transparent windows badly.
- Bar (44 px, the drag handle): Start/Stop button showing the call timer while running;
  one level dot per side whose colour is the stream state; the Ask box with its screen
  toggle; the shield; a chevron to collapse or expand the panel; a menu with Quit and
  Click-through.
- Click-through is switched on from the menu or Ctrl+Shift+M and switched off with
  Ctrl+Shift+M, as today; while it is on the bar shows "Click-through on, Ctrl+Shift+M
  to use Echo" and the Ask box cannot be typed in.
- Panel tabs: Live, Transcript, Context, Settings.
  - Live: "They said" with the latest "them" line and its meaning; the Answer card; the
    echo-removed count.
  - Transcript: the full two-sided transcript, each "them" line with its meaning.
  - Context: folder, file list with skipped files and reasons, Reload, the note about
    me and this call.
  - Settings: what the settings panel has today, minus the context note, plus
    `myLanguage`, `explainThem`, `contextBudgetChars` and `llmVisionModel`. Replay file
    pickers and Demo move here under Audio.
- States that must exist: first-run consent; no key; no context folder ("Add a context
  folder so Echo can answer from your files"); context folder unreadable or empty; idle
  with context; starting; live with nothing said yet; answer checking (streaming); each
  of the six verdicts; model unreachable; prompt too long for the model; reading the
  screen; no vision model set; model cannot read images; could not read the screen;
  demo mode (recordable); stream reconnecting; stream error; click-through on; replay
  finished and saved.
- The panel opens by itself when a call starts and when an answer arrives. The chevron
  and Ctrl+Shift+H behave as today.
- Look: dark translucent glass, hairline border, one accent colour, system UI font with
  Nirmala UI for Indian scripts. The detailed visual system is set in the design review
  that follows this doc.

### Hidden from screen share

`setContentProtection(true)` is already called in `src/main/overlay-window.ts:43`. It
has never been checked on Windows. It becomes a tested claim.

- The check: by hand on this machine, against a real screen share and a screen
  recording, with the transparent window and again with `ECHO_OPAQUE_WINDOW=1`. It
  passes only if the overlay is absent in all four.
- The main process holds one constant listing where the check passed: the platform and
  the lowest OS build tested. It starts empty. After the check passes here, this
  machine's Windows build number goes in.
- The shield reads "Hidden from screen share" only when the running platform and build
  are covered by that constant and demo mode is off. Everywhere else, macOS and Linux
  included, it is an amber icon reading "May be visible when sharing".
- If the check fails on Windows, the constant stays empty, the shield stays amber, the
  README says what was observed, and the matching success criterion is reported as not
  met. The rest of the product does not depend on it.
- Recording the demo: a protected overlay does not appear in a screen recording, so the
  video could not show it. `ECHO_RECORDABLE=1`, read only by the main process like
  `ECHO_OPAQUE_WINDOW`, turns protection off; the shield then reads "Visible in
  recordings (demo mode)" in amber. The video proves the hidden claim with a second
  clip: a real screen share with protection on, showing the sharer's screen with the
  overlay next to the viewer's screen without it.

## Success Criteria

- With the mock servers and no keys: load `demo-context/`, start the demo replay, and
  see a "from your files" answer with the right source file for the stock question, a
  "not in your files" card for a question the files do not cover, and a meaning line
  under a mixed-language line.
- With real keys (waived if the real API cannot be reached, see Next Steps 2): the same
  demo runs start to finish on Windows twice in a row with no manual fixes.
- First words of an answer appear within about 2 seconds of the caller's final
  transcript line on a hosted model.
- An answer is shown as "from your files" only when its numbers appear in what was
  sent; covered by unit tests of the number check, and each demo answer is checked by
  hand against the demo files on the model used for the video.
- With a vision model set, the screen hotkey with a question visible on screen produces
  an answer titled "from your screen". With none set, it shows the "set a vision model"
  message. No screenshot file exists on disk afterwards.
- With no context folder set, the app behaves as it does today apart from the layout.
- The overlay does not appear in a Windows screen share or screen recording on this
  machine; if it does, this criterion is reported as not met (see Hidden from screen
  share).
- `npm run lint`, `npm run typecheck` and `npm test` pass on Windows, with new tests for
  the context engine, the source parsing, the number check, the verdict order, trigger
  precedence, the meaning engine, screen message building and the UI reducer.
- Live mic plus system-audio loopback moves both level meters and produces transcripts
  on this Windows machine. The mock Gnani server is enough to pass this; real text needs
  the real key.

### R1-1 — consistency (blocking)

**Problem**

> The `screen` verdict is missing from the single verdict-order rule. 'Reading the screen' adds a sixth verdict `screen`, 'placed first in the order', but the 'Verdict order (R2-3)' decision lists seven rules, says 'one rule, first match wins', starts with 'No context folder loaded: reply', and never mentions `screen`. A screen answer with no context folder is therefore both `screen` and `reply`, and it is undefined whether `missing` or a dropped-file citation can override `screen`.

**Remedy**

> Add `screen` to the R2-3 ordered list at an explicit position (the body says first: image attached and request succeeded) and state how it interacts with rule 1 (no folder), rule 3 (`missing`) and rule 6 (all cited files dropped).

### R1-2 — consistency (minor)

**Problem**

> The verdict count is stale in four places: Answers lists five, the Live tab says 'each of its five verdicts', the required states say 'the five answer verdicts', and Next Steps 4 says 'the five verdicts', while the screen section makes it six.

**Remedy**

> Say six verdicts (or 'every verdict') everywhere and list `screen` alongside the other five in the Answers section.

### R1-3 — consistency (blocking)

**Problem**

> Screen questions without a call contradict the Ask box rule. Answers says 'Typed questions work only while a call is running; before a call the Ask box is disabled'. The screen section says the screen toggle lives on the Ask box, attaches the screen to the typed question, and 'Works with or without a call running'. ### R1-9 — feasibility (blocking)
